## 3. How the accuracy is known without a single labelled invoice

The dependency that normally makes this impossible is human-labelled documents.
It is removed by running the arrow the other way:

```
canonical JSON  ->  rendered document  ->  reader  ->  compare to canonical
                (never: reader output  ->  expected)
```

`expected` is not stored judgement. It is a pure projection of `raw_fields`
computed by exactly one function, `build_ground_truth.expected_from`, which
takes no argument any reader has touched. The right answer is known because the
document was rendered *from* it.

### The forgery this is designed to make impossible

Somebody runs a reader, it disagrees, and they "fix" the corpus by pasting the
reader's answer into `expected`. Every test still passes. The benchmark now
measures nothing and looks exactly like one that works.

Three values are locked into a ring, and no single edit leaves it intact:

| Link | Derived from | Broken link reports |
|---|---|---|
| `generation_hash` | `raw_fields` + `gst_context` + `generation_version` | `STALE_GENERATION_HASH` |
| `expected` | `raw_fields`, via `expected_from` | `EXPECTED_NOT_FROM_TRUTH` |
| `sha256` / the bytes | `raw_fields`, via `render` | `STALE_DOCUMENT_HASH`, `DOCUMENT_NOT_A_REBUILD` |

A hole was found while proving this rather than assumed away: a forger who
edits `raw_fields`, re-derives `expected` **and** recomputes `generation_hash`
produces a case file that is internally perfect and describes a different
document. `CASE_NOT_A_REBUILD` closes it — this corpus is generated, so every
case file must equal what the generator produces for it. The test that proves
it asserts that finding is the **only** one raised, i.e. that every other net
was genuinely evaded.

### The conservation law

`subtotal + tax_amount == total` on all 100 cases, and where a case has line
items, `sum(line_items) == subtotal`. Two quantities that must be equal need no
expert and no label. A discount is carried as a **negative line item**
precisely so the law keeps holding rather than acquiring an exception.

### Corpus labels — the four-way vocabulary, and why two are zero

```
SYNTHETIC_EVIDENCE              100
THIRD_PARTY_PUBLIC_EVIDENCE       0
REAL_ANONYMISED_EVIDENCE          0
HELD_OUT_CUSTOMER_LIKE_EVIDENCE   0
```

The label describes **the bytes, not the words**. Every byte in this corpus was
generated by `scripts/build_ground_truth.py`, so every case is
`SYNTHETIC_EVIDENCE`.

Fifty of the hundred carry a supplier name copied **byte-for-byte** out of a
published UK government spend file — `Q5 = C`, public data where it fits. That
is recorded per case as `content_source`, cites the department, and is checked
against the committed original file rather than trusted:
`test_every_public_supplier_name_appears_verbatim_in_the_cited_file`. All seven
departments already recorded in `accountant/ingest/sources.py` are drawn on, so
the URL, licence (Open Government Licence v3.0) and retrieval date are cited by
code rather than restated.

Calling a generated PDF `THIRD_PARTY_PUBLIC_EVIDENCE` because a real supplier
name appears inside it would be exactly the mislabelling `Q5` forbids. The two
real-evidence labels are zero because they require real bills, which is `H-02`,
which is optional and unsupplied — and a test enforces that no generated case
may ever wear one.

## 5. The gate, and the numbers against it

Owner-set gate:

```
date >= 95/100 · party >= 95/100 · total >= 95/100 · tax >= 95/100
line items >= 95/100 · silent blanks = 0 · 100/100 processed or explicit
not_found · reader output provenance = 100%
```

| Backend | date | party | total | tax | line items | gate |
|---|--:|--:|--:|--:|--:|---|
| `StubExtractor` | 0/100 | 0/100 | 0/100 | 0/100 | 0/100 | **FAIL** |
| `UnavailableExtractor` | 0/100 | 0/100 | 0/100 | 0/100 | 0/100 | **FAIL** |
| `TypedTextExtractor` (`DEFAULT_BACKEND`) | 0/100 | 0/100 | 0/100 | 0/100 | 2/100 | **FAIL** |
| `OracleExtractor` (answers from the truth) | 100/100 | 100/100 | 100/100 | 100/100 | 100/100 | PASS |

For all four: `processed = 100/100`, `silent blanks = 0`,
`unclassified failures = 0`, `reader output provenance = 100/100`.

**A failing accuracy gate against a stub is a working benchmark, not a broken
build.** The 95 threshold is deliberately **not** wired into pytest — a
benchmark that turns the build red because a stub scores zero is deleted within
a week. It belongs in the runner's exit code, which the second agent owns. What
pytest asserts is that the *harness* is correct, including that a stub scores
nothing.

### Why the oracle row exists

Every real backend scores zero. A comparator that was simply broken would also
score zero, and the two are indistinguishable without a case that is supposed
to score full marks and does. `OracleExtractor` is handed the answer key and
never looks at the document; it exists so that a zero elsewhere is a
measurement rather than a bug. Two further oracles, each wrong on one field
only, score 0 on that field and 100 on the other four — which is what makes the
per-field gate meaningful rather than one number wearing five names.

### Two results in that table worth reading twice

**`typed_text` fabricates 20 totals.** The production default states
`per_field_source["total_paise"] == "typed_text"` for 20 cases and the number
is wrong in all 20. That is not a blank and not a refusal: it is an invented
value carrying a real backend's name. On `GT-0001` it reports ₹1.00 for an
invoice of ₹147.50, because `INVOICE NO: GT/0001` is the first digit run on
the page.

**`typed_text` scores 2/100 on line items, and both are coincidence.** Both are
cases whose canonical line-item list is empty; this backend returns an empty
list unconditionally and never looks. Recorded rather than smoothed away.

### The scoring rule that stops a stub scoring by accident

Ten of the hundred cases legitimately have no line items. A naive comparator
hands a silent backend 10/100 for agreeing by accident — measured, before the
rule was added. The rule: **a field is correct only if the reader stated a
source for it.** A record whose every source is `not_found` answered nothing,
and nothing is never right.

## 7. What was rendered honestly, and what is BLOCKED

`pyproject.toml` declares `dependencies = []` and exit 7.3 forbids a reader, so
no PDF, image or DOCX library may be added. Every container is written out of
the standard library.

| Type | Fidelity | Verified how | Status |
|---|---|---|---|
| text | `native_text` | UTF-8 decodes strictly | rendered |
| PDF | `text_operators` | every xref offset points at the object it names; `%PDF-1.4` header and `%%EOF` trailer | rendered |
| PNG | `rendered_raster` | CRC32 matches every chunk; IDAT decompresses to exactly `(width+1) x height` bytes; every image carries >500 inked pixels | rendered |
| DOCX | `native_text` | `zipfile` opens it, `testzip()` returns `None`, all four OOXML parts present, `<w:t` runs carry the text | rendered |
| JPG | `container_only` | SOI/APP0/COM/EOI marker walk lands exactly on EOI; **no SOF marker**, asserted | **`BLOCKED`** |

### The JPG limitation, stated plainly

A baseline JPEG needs a DCT plus Huffman entropy coding. With no image library
permitted, **nothing here can verify that anything it emitted decodes.**
Shipping an unverifiable encoder and calling its output a JPEG would be a claim
with no measurement behind it, which is the thing this project exists to
prevent.

So the JPG cases are **real JFIF-framed containers carrying the invoice text in
COM comment segments and no encoded image data.** They are not photographs, the
manifest says `container_only`, a test asserts no start-of-frame marker is
present, and the slice is `BLOCKED`. What would unblock it: a verifier, which
means either a permitted image library (an owner decision, and it would breach
`dependencies = []`) or a hand-written decoder, whose agreement with a
hand-written encoder would prove self-consistency and not conformance.

The PNG glyphs are drawn from a 5x7 bitmap font written by hand. Drawing glyphs
is generation, not image analysis — nothing inspects a picture, it emits one —
and it sits in `scripts/`, outside the package the AST guard covers. The
renderer **raises** `UnrenderableGlyph` on a character it cannot draw rather
than leaving an empty box, and that guard is proved by making it fire.

### What is still `NOT_MEASURED` about the documents

That the PDFs open in a PDF viewer, or the PNGs display in an image viewer. No
library is permitted to look. What is proved is structural.

## 8. The one production change, and why it could not be a fixture

`accountant/extract/adapter.py` — `TypedTextExtractor` now honours the `mime`
argument it already received and previously discarded as `_mime`, and decodes
strictly.

Measured **before** the change, on the five input types:

```
%PDF-1.7 ...            total_paise = 170       source "typed_text"
PNG with a tEXt chunk   total_paise = 420000    source "typed_text"
JPEG with a COM         total_paise = 3133700   source "typed_text"
```

None of those is a blank and none is a `not_found`. Each is an invented number
wearing a real backend's name — worse than either, because a refusal is visible
and asks the person a question, and an invented total does not.

A second case, on the encoding four of the seven published UK government files
actually use. `"paid Café Ltd 4200 for supplies"` in cp1252 returned
`party == "Caf"`, sourced `typed_text`: the é became U+FFFD under
`errors="replace"`, the party pattern stopped at it, and a **truncated supplier
name** went on to `propose_account`, where a name that does not match history
is a new vendor. A wrong party is not a missing party.

**Why not a fixture-only change.** No arrangement of bytes on disk stops a money
regex matching the digits in `%PDF-1.7`. Choosing documents that happen to dodge
it is tuning a corpus to pass, which is the failure this PR exists to prevent.
And the corpus needs expected outputs: recording `total = 170` as *expected*
would enshrine the fabrication as correct behaviour.

**Why it is the smallest change.** It adds no abstraction and no new class. It
uses the parameter the `Extractor` Protocol has always passed, and it builds
the refusal record with `UnavailableExtractor` — the one class in the package
that builds an all-`not_found` record — for the reason
`registry.GuardedExtractor.outage` already gives: two places that build that
shape is how one of them ends up without a reason on it, which is a silent
blank wearing a label.

**What it is not.** It is not a reader. No container is parsed and no byte is
interpreted; the backend states what it can read and refuses everything else
with a sentence saying why. `text/plain; charset=utf-8` is accepted — refusing
over eight trailing characters would be a refusal nobody could act on — and a
typed sentence with genuine UTF-8 accented letters still reads, which is the
disconfirming case for the strict decode.

the schema is a third place for it to drift. `scripts/run_ground_truth.py`
belongs to the second agent and imports `score_corpus` from there. Nothing
under `artifacts/ground_truth/rules/`, `accountant/rules/` or `accountant/tax/`
was created or touched.

## 10. Proving the guards are load-bearing

Each mutant was injected by hand into the committed tree, the suite was run,
and the tree was restored. A guard that stays green when broken proves nothing.

| # | Mutant | Result |
|---|---|---|
| M1 | a field returns a silent blank instead of an explicit `not_found` | **RED** — 3 failed |
| M2 | a case loses its corpus label | **RED** — 5 failed |
| M3 | a case loses its provenance | **RED** — 7 failed |
| M4 | `expected` overwritten with what the reader actually said | **RED** — 7 failed |
| M5 | `raw_fields` edited, hash left stale | **RED** — 6 failed |
| M6 | one input type dropped from the corpus (20 JPG cases deleted) | **RED** — 18 failed |
| M7 | one input type dropped from the builder (`INPUT_TYPES` loses JPG) | **RED** — 9 failed |
| M8 | a document edited by hand to flatter a reader | **RED** — 8 failed |
| M9 | the scorer stops asking whether the reader answered (coincidence counts) | **RED** — 2 failed |
| M10 | the media-type gate removed (the fabrications come back) | **RED** — 6 failed |
| M11 | strict decode reverted to `errors="replace"` | **RED** — 1 failed |
| M12 | the scorer can never award a mark | **RED** — 3 failed |

Restored after every one: 57 passed in the corpus file, 162 passed across the
two files exercised.

A thirteenth was tested inside the suite rather than by hand, because it is the
hardest one: a **self-consistent forgery** — `raw_fields` edited, `expected`
re-derived and `generation_hash` recomputed. It evades every net except
`CASE_NOT_A_REBUILD`, and the test asserts that finding is the only one raised,
so the claim "this net is the one that catches it" is measured rather than
described.

## 12. What this does not prove

- **That any backend reads a bill.** Nothing here is a reader. The production
  backend is `NOT_SELECTED` (`H-01`).
- **That the corpus predicts real-bill accuracy.** It does not, and it must
  never be quoted as if it did. Generated documents are not bills. Real-bill
  accuracy is `NOT_MEASURED` and is unblocked only by `H-02`.
- **That the documents are visually correct.** Structural verification only;
  no library may look.
- **That the JPG slice measures anything.** It is `BLOCKED`, and the 80/100
  ceiling it imposes is stated in the manifest rather than left for somebody to
  discover.
- **That `rule_ids` are populated.** They are empty on all 100 cases. The rules
  corpus is another workstream's; a non-empty `rule_ids` today is a dangling
  reference and the validator refuses it.
- **Anything about GST posting.** `NOT_IMPLEMENTED` per `Q3`, and untouched.
